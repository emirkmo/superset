# Local 6.1.3 release candidate

This candidate extends local tag `6.1.2`
(`d923b1ce818fe2c45e96c9cb6f2728c0a9fcdfb3`) and preserves its dropdown,
dashboard-owner, and required-filter fixes. It is not an Apache Superset release.
The original source baseline matches `apache/superset:6.1.0-py312`.

## Change and provenance

[PR #40993](https://github.com/apache/superset/pull/40993), merged commit
`257dafeec51a62c6bac9d648b7c284020b1fe718`, parent
`6d08e79259a327fa60b7a6d7e9a7808de2afb839`, prevents query generation from
mutating caller-owned ad-hoc ORDER BY metrics. The production change matches
upstream: process a shallow copy of the metric dictionary before replacing its
SQL expression. The modified field is a string; no nested object is modified.

With global async queries, the worker computes the dataframe cache key before
SQL generation. Processing an ORDER BY expression can render Jinja or normalize
CRLF/whitespace. Mutating the shared metric writes that processed expression into
the query context subsequently cached by the worker. The result-retrieval GET
then reconstructs a different dataframe cache key and its cache-only lookup can
return HTTP 422, `Error loading data from cache`.

The worker supplies the `qc-...` result URL; the client does not calculate it.
This fix addresses that mutation mechanism. It does not establish the cause of
every cache error: expiry, eviction, write failures, or mismatched web/worker cache
configuration can also produce failed cache-only lookups. The user's production
incident has not been independently reproduced.

Only the test import context conflicted with the 6.1.2 harness. Required imports
were adapted without importing later tests or refactors. An additional regression
checks dataframe cache-key stability through serialized query-context rehydration.
There are no dependency, migration, frontend behavior, or Dockerfile changes.

## Validation

Backend tests use Python 3.12 in a temporary venv provisioned with `uv`, base
requirements and pytest-mock. From the backport worktree:

```bash
/tmp/superset-613-venv/bin/pytest -q \
  tests/unit_tests/models/helpers_test.py --disable-warnings
```

The model-helper suite passes all 46 tests. The four regressions cover CRLF,
Jinja, cache-key stability across SQL construction, and serialized query-context
rehydration. Removing only the production dictionary copy makes all four fail;
restoring it makes all four pass. Tests also check that SQL remains processed.

The 12 frontend suites covering the previous local fixes pass all 281 tests.
They ran in the original 6.1.2 worktree, whose frontend source is identical to
this candidate apart from version metadata. An initial run using shared
node_modules symlinks in the separate worktree failed two FilterBar tests due to
duplicate module identity/client configuration; the original-worktree run passed.
No frontend test or application code was changed to accommodate that harness.

Independent agent review, repository hooks, and publication evidence are recorded
in the accompanying release commit and final handoff. A full async browser or
HTTP POST-to-Celery-to-GET smoke test was not performed: no running app, metadata
database, or shared Redis services were available. The unit tests exercise real
SQL construction and query-context serialization, but do not replace that test.

## Candidate naming and build

Source and image tag: `6.1.3rc1`. Package metadata: `6.1.3-rc.1`, which npm semver
accepts and Python packaging normalizes to `6.1.3rc1`. Existing Apache source RC
tags use the same `rc1` spelling; their package metadata uses the final numeric
version. This local candidate explicitly marks its package metadata as prerelease.
Only package.json and the two root package-lock version fields change; dependency
lock entries remain unchanged.

The separate publishing helper workflow checks out the full reviewed release SHA
and builds the original Dockerfile with target `lean`,
`PY_VER=3.12.14-slim-bookworm`, platform `linux/amd64`. It publishes
`ghcr.io/emirkmo/superset:6.1.3rc1` plus a source-SHA-qualified tag, preserving
the previous image tags. Pin deployments to the verified manifest digest in the
final handoff.

## Deployment smoke test

In staging, enable `GLOBAL_ASYNC_QUERIES` with polling and a Redis-backed
DATA_CACHE_CONFIG shared by web and Celery workers. Create a custom SQL metric
with CRLF newlines, leave explicit sorting empty so the metric supplies ORDER BY,
and force-refresh the chart. Wait for async completion and GET the returned
result_url: expect HTTP 200 and correct chart data. Repeat with cache reuse and
with a Jinja expression when template processing is enabled. Compare dataframe
cache keys at execution and retrieval; they must match.

Repeat on an affected dashboard, keeping chart caching enabled. Verify initial
load and force-refresh, then rerun the earlier required-default-filter, dropdown,
and dashboard-owner smoke checks. Record the tested image digest and responses.
If the same error persists, inspect cache TTL/eviction and shared web/worker cache
configuration rather than assuming this mutation is the only possible cause.
